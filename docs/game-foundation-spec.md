# 黑暗森林首版联机底座

## Problem Statement

《黑暗森林》目前有一个可渲染的 3D 像素风场景。我们需要在此基础上做出一局能联机、能按玩家隔离迷雾信息、能重连和复盘的格子对局。具体玩法还会迭代，首版需要先验证回合、占位、视野和对峙能在同一套规则中运行。

## Solution

两名玩家在同一张单层逻辑地图上各自规划移动，再由房间统一锁定计划、逐拍结算。每位玩家只收到自己的玩家视图，能从画面看出当前视野、过去的目击和回合进度。互相看见的玩家进入对峙并停留到本轮结束。房间继续推进，玩家断线后可回到原座位，开发者可以重放已记录的回合。

首个里程碑交付一张地图、两个可联机的棋子和一局可复现的对局。另用三人场景验证局部对峙。

## User Stories

1. 作为玩家，我希望能和另一名浏览器玩家进入同一个房间，以便在同一张逻辑地图上试玩。
2. 作为玩家，我希望开局能看到公开的地图结构，以便规划路线。
3. 作为玩家，我希望知道当前的回合、阶段和剩余时间，以便在截止前锁定行动计划。
4. 作为玩家，我希望各自秘密提交行动计划，以便同时做选择。
5. 作为玩家，我希望能确认自己的计划是否锁定，以便知道本轮会结算哪些行动。
6. 作为玩家，我希望相邻格之间允许斜向移动，以便按棋盘布局选择路线。
7. 作为玩家，我希望每轮最多安排两次移动，以便判断自己和对手本轮的移动范围。
8. 作为玩家，我希望每格最多站一人，以便根据占位判断路线。
9. 作为玩家，我希望同一拍的行动统一结算，以便结果由规则决定。
10. 作为玩家，我希望一步受阻后，后续动作仍按原计划的拍数检查，以便还有机会执行符合当前条件的动作。
11. 作为玩家，我希望看见周围一圈含斜角的可见动态，以便判断身边的空间。
12. 作为玩家，我希望门墙能遮挡视线，以便用地形隐藏行动。
13. 作为玩家，我希望圈外和遮挡后的动态信息留在迷雾中，以便依靠观察推断对手的位置。
14. 作为玩家，我希望能在结算中看见短暂出现的目标，以便使用这一拍获得的信息。
15. 作为玩家，我希望从地图记忆分辨目击位置和当前视野，以便区分旧信息与眼前变化。
16. 作为玩家，我希望与对手互相看见时触发对峙并各自停在原地，以便在下一轮的行动阶段做决定。
17. 作为第三名玩家，我希望其他玩家触发对峙时自己的行动仍能结算，以便按计划继续本轮。
18. 作为对峙的参与者，我希望下一轮仍与其他玩家一起进入计划阶段，以便在统一的回合里继续行动。
19. 作为玩家，我希望网络重发同一请求时只处理一次，以便避免重复应用计划。
20. 作为玩家，我希望超时未锁定的座位按等待结算，以便房间继续推进。
21. 作为已锁定计划后断线的玩家，我希望计划仍能执行，以便本轮结果符合我最后确认的安排。
22. 作为重连的玩家，我希望恢复原座位、当前视野、地图记忆、已获知的提示、锁定状态和剩余时间，以便继续参与对局。
23. 作为玩家，我希望在现有像素风场景中看到棋子、迷雾和结算片段，以便从画面读懂本轮结果。
24. 作为关卡设计者，我希望能用数据描述地图上的格子、地面和格边，以便用同一套规则验证不同布局。
25. 作为开发者，我希望能够调节距离和移动上限等配置，并在规则模块中加入新行为，以便逐步拓展玩法。
26. 作为开发者，我希望用已记录的输入和对应版本复现结果及逐拍观察，以便定位结算和可见性问题。

## Implementation Decisions

- 逻辑地图公开，首版采用单层格子。地面属于格子，门窗属于格边，动态地形状态和玩家位置属于权威对局状态。占位从玩家位置得出。通行和视线分别查询棋盘。
- 房间共用计划阶段和结算阶段。房间负责时钟、锁定、超时和身份，每局通过同一入口提交状态变更。命令绑定玩家、回合编号和请求编号。旧回合命令无法修改当前回合。
- 规则引擎在同一拍起始状态上统一裁决，并在提交拍结果时保证每格最多一名玩家。移动额度与拍数独立。斜向移动和翻窗各占一次移动额度。普通行动失败后按原有拍数检查其余动作。
- 对峙关系和本轮停止分别记录。互相可见触发对峙后，参与者当轮原地停留，其他玩家继续。下一轮各玩家共用同一计划阶段，规则仍能读取对峙记录。
- 服务端逐拍生成每位玩家获准获得的观察事实，再通过玩家视图发送当前状态和可播放片段。短暂目击带回合和拍数。玩家只接收公开地图、自身状态和获准获知的动态。提交反馈也遵守这个边界。
- 玩家重连时回到原座位并获取当前玩家视图。已经锁定的计划照常执行。截止时尚未锁定的座位按等待结算。
- 使用已确认的技术栈。浏览器沿用 Three.js、Vite 和 DOM，新增底座使用严格模式 TypeScript 与 npm。Node.js 24 LTS 服务端通过 `ws` 与浏览器原生 WebSocket 交换 JSON 消息。Zod 校验消息和地图数据，规则引擎判断行动是否可执行。服务端状态类型与公开协议分开。
- 单服务进程在内存中维护活动房间，以权威快照作为当前状态。开发复盘输入按轮写入本地 JSON Lines 文件。记录初始状态、地图与规则版本、已锁定计划及超时补入的等待。规则使用随机时保留种子。复盘加载对应版本，重跑同一个规则引擎。
- Three.js 将玩家视图映射为棋子、迷雾和动画。房间决定回合时序，客户端显示服务器给出的截止时间。地图布局、距离和移动上限走配置，新增行为走规则代码。

## Testing Decisions

- **主要测试入口是房间的公开流程。** Vitest 从创建测试房间、提交和锁定计划开始，再推进到截止、结算和读取玩家视图。用可控时钟安排截止，断言位置、行动结果和各玩家收到的实际信息。测试使用规则引擎、视图和房间的正常协作路径，检查可观察行为。
- **规则和信息隔离。** 验证开阔处斜向移动、每轮两次移动上限、占位唯一、普通受阻后下一拍仍检查，以及门墙遮挡与一圈视野。比较同一局的不同玩家视图，核对短暂目击、地图记忆和实际下发的结算片段。检查未获准的计划、位置、路径和内部事实是否留在服务端。
- **局部对峙。** 在同一房间放入三名玩家。让其中两名互相可见，检查两人当轮停留、第三人完成行动，以及三人进入同一个下一轮计划阶段。
- **联机验收。** Playwright 用两个隔离的浏览器会话走真实连接和页面流程。验证提交、重发、截止、超时、断线期间对局照常推进和重连恢复。用客户端实际收到的消息核对迷雾边界，并确认画面能展示对应视图。
- **开发复盘。** 从一次实际对局写出的记录重跑已记录回合，核对权威结算结果与每位玩家的逐拍观察一致。
- **现有先例。** 当前项目的可运行入口是暮林石室的渲染预览。表现层验收沿用项目像素风格规范。规则、房间和复盘测试随底座建立。

## Out of Scope

- 遗物争夺、得分和胜负、撤离点、拼格背包、截击、诱饵及完整线索系统。
- 同格争抢的具体胜负、斜向穿过墙角的裁定、两点动作的生效时机，以及对峙中具体可执行的动作。首版结构需保留这些规则的裁决位置。
- 服务进程重启后继续活动房间。重启后使用已写入的回合记录供开发复盘。

## Further Notes

按「无画面结算、逐拍生成玩家视图、双浏览器联机」的顺序推进。对局术语以项目术语表为准。模块边界和技术选型以已确认的《黑暗森林对局架构》和《首版技术栈》ADR 为准。
